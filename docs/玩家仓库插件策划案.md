# SoulWarehouse 玩家仓库插件策划案

## 1. 项目结论

根据你刚才确认的信息，`SoulWarehouse` 首版正式定位如下：

- 服务端版本：`1.12.2`
- 插件类型：`纯私人仓库`
- 经济系统：`不接 Vault`
- 管理员查看他人仓库：`只读`
- 数据库：`MySQL`

这意味着首版目标非常明确：

> 做一个基于 TabooLib、面向 1.12.2 服务端、稳定可靠的多页私人玩家仓库插件。

## 2. 产品定位

插件核心价值：

- 给玩家提供随时可用的私人仓库存储空间
- 给服主管理提供安全、可控、只读审查能力
- 给后续开发保留清晰的扩展空间

首版不追求“大而全”，重点是：

- 稳定
- 好用
- 不刷物
- 容易上线

## 3. 版本边界

本策划案只针对 `1.12.2` 版本的 Bukkit/Spigot/Paper 生态。

因此设计上遵循以下边界：

- 优先适配 `1.12.2` 的物品与背包交互逻辑
- 不把首版复杂度浪费在高版本特性兼容上
- 界面与交互尽量贴近老版本玩家习惯
- 代码仍基于 TabooLib 组织，保留以后扩版本的可能

## 4. 核心目标

### 4.1 玩家目标

- 输入命令即可打开私人仓库
- 拥有多页可切换仓库存储空间
- 菜单简单直观，低学习成本
- 存取物品稳定，不丢物、不复制

### 4.2 管理目标

- 支持查看任意玩家仓库
- 管理员查看模式固定为只读
- 支持重载配置、强制保存、排查异常
- 可通过权限节点控制可用仓库页数

### 4.3 开发目标

- 基于 TabooLib 的命令、菜单、配置体系实现
- 菜单层、业务层、数据层分离
- MySQL 持久化与内存缓存配合，兼顾性能与安全

## 5. 插件核心玩法

### 5.1 玩家使用流程

1. 玩家输入 `/warehouse` 或 `/sw`
2. 打开仓库主页
3. 选择可用仓库页
4. 在仓库页内存取物品
5. 关闭菜单时自动保存当前页

### 5.2 管理员使用流程

1. 管理员输入 `/warehouse open <player>`
2. 打开目标玩家的仓库主页
3. 选择某一页查看
4. 以只读方式浏览仓库内容
5. 不允许编辑、拖拽、交换、取出、放入

## 6. 功能范围

## 6.1 MVP 必做功能

### A. 私人多页仓库

- 每名玩家拥有多页私人仓库
- 每页仓库固定容量
- 可按页切换
- 仓库数据独立保存

### B. 权限解锁页数

- 默认页数由配置定义
- 权限节点决定玩家最终可访问页数
- 未解锁页面在主页显示为锁定状态

### C. 菜单系统

- 仓库主页菜单
- 仓库页菜单
- 未解锁页提示
- 管理员只读模式提示

### D. 数据持久化

- 玩家仓库页数据保存到 MySQL
- 玩家基础档案保存到 MySQL
- 支持缓存加载与脏页保存

### E. 管理命令

- 重载配置
- 强制保存缓存
- 查看他人仓库

## 6.2 首版不做

为了保证项目收敛，以下内容明确不进入首版：

- 共享仓库
- 公会仓库
- Vault 付费解锁
- 仓库搜索系统
- 自动整理系统
- 仓库页自定义命名
- 审计日志系统

这些功能可以作为后续版本扩展点，但不应进入 MVP。

## 7. 菜单策划

## 7.1 仓库主页

用途：展示玩家所有仓库页入口。

建议容器：`Chest 6 行`

建议布局：

- 中部区域：仓库页入口按钮
- 底部左侧：帮助/说明
- 底部中间：刷新
- 底部右侧：关闭

每个仓库页按钮显示：

- 页码
- 是否解锁
- 状态说明
- 点击提示

### 已解锁页

- 显示绿色或普通图标
- 点击进入对应仓库页

### 未解锁页

- 显示灰色/锁定图标
- 点击后提示“该页未解锁”

## 7.2 仓库页菜单

用途：玩家真实存储物品。

建议布局：

- 第 1-5 行：实际仓库存储区，共 `45` 格
- 第 6 行：功能栏

功能栏建议：

- 返回主页
- 上一页
- 下一页
- 当前页信息
- 关闭菜单

## 7.3 管理员只读查看页

管理员查看他人仓库时，不直接复用普通存储页行为，而是单独定义只读逻辑：

- 可浏览
- 不可放入物品
- 不可取出物品
- 不可 shift-click
- 不可数字键交换
- 不可拖拽
- 不可双击聚合

标题建议：

- `&8查看仓库 - {player} - 第 {page} 页`

## 7.4 TabooLib 菜单实现建议

- 仓库主页：使用 `BukkitUI` 的 `Chest`
- 玩家仓库页：使用 `StorableChest`
- 管理员只读页：使用 `Chest` 或对 `StorableChest` 全事件锁定

我的建议是：

- 玩家自己的仓库页用 `StorableChest`
- 管理员查看他人仓库单独做一个只读菜单

这样比“同一个菜单硬切模式”更稳，尤其是 `1.12.2` 这类老版本交互里，越简单越安全。

## 8. 命令设计

### 玩家命令

- `/warehouse`：打开仓库主页
- `/warehouse open <page>`：直接打开指定页
- `/sw`：`/warehouse` 别名

### 管理员命令

- `/warehouse open <player>`：查看目标玩家仓库主页
- `/warehouse open <player> <page>`：查看目标玩家指定页
- `/warehouse reload`：重载配置
- `/warehouse saveall`：保存所有缓存仓库

### 不纳入首版的命令

- `/warehouse buy`
- `/warehouse unlock`
- `/warehouse rename`
- `/warehouse share`

因为首版没有经济系统，也没有共享与页重命名设计。

## 9. 权限设计

### 基础权限

- `soulwarehouse.use`
- `soulwarehouse.command.open`

### 仓库页权限

- `soulwarehouse.page.1`
- `soulwarehouse.page.2`
- `soulwarehouse.page.3`
- `soulwarehouse.page.4`
- `soulwarehouse.page.5`
- `soulwarehouse.page.*`

### 管理员权限

- `soulwarehouse.admin`
- `soulwarehouse.admin.open.others`
- `soulwarehouse.admin.reload`
- `soulwarehouse.admin.saveall`

说明：

- 由于管理员查看为只读，因此不需要 `edit.others` 权限
- 页数权限建议和配置默认页数组合判断，避免权限与配置冲突

## 10. 数据设计

## 10.1 数据库方案

你已经确认使用 `MySQL`，因此首版数据层按以下原则设计：

- 所有正式数据以 MySQL 为准
- 玩家打开仓库时先载入内存缓存
- 玩家关闭仓库或插件关闭时回写数据库
- 避免每次点击都实时写数据库

## 10.2 表结构建议

### 表 1：`sw_player_profile`

存储玩家基础信息。

字段建议：

- `uuid` `varchar(36)` 主键
- `name` `varchar(32)`
- `max_pages` `int`
- `created_at` `bigint`
- `updated_at` `bigint`
- `last_open_at` `bigint`

### 表 2：`sw_player_warehouse_page`

存储每个玩家的每页仓库内容。

字段建议：

- `id` `bigint` 自增主键
- `uuid` `varchar(36)`
- `page` `int`
- `content` `longtext`
- `updated_at` `bigint`

索引建议：

- 唯一索引：`uniq_uuid_page(uuid, page)`
- 普通索引：`idx_uuid(uuid)`

## 10.3 仓库内容存储方式

首版建议按“整页序列化”存储，而不是逐格拆表：

- 一个玩家一页仓库 = 一段序列化文本
- `content` 字段保存整个 `45` 格内容

推荐原因：

- SQL 结构简单
- 查询直接
- 缓存命中清晰
- 关闭页面时可整页保存

## 10.4 序列化方案建议

对于 `1.12.2`，建议序列化时优先考虑稳定性：

- 以 Bukkit `ItemStack` 序列化为基础
- 转成字符串后存入 MySQL `longtext`
- 空槽位统一写成 `null`

不要在首版做过度复杂的自定义压缩协议，先保证可靠和可恢复。

## 11. 缓存与保存策略

建议维护以下内存结构：

- `warehouseCache`：缓存已加载的页数据
- `dirtyPages`：被修改但未保存的页
- `openSessions`：当前打开中的玩家会话

### 保存时机

- 玩家关闭仓库时保存
- 玩家退出服务器时保存
- 插件关闭时统一保存
- 管理员执行 `/warehouse saveall` 时保存

### 是否定时自动保存

首版建议：

- 可以配置定时自动保存
- 但自动保存只处理脏页
- 不做高频保存

建议默认值：

- `300` 秒一次

## 12. 安全与防刷设计

`1.12.2` 的仓库插件必须优先考虑交互安全。

### 必做限制

- 一个玩家同一时间只允许一个私人仓库会话
- 页面切换前强制处理当前页保存/缓存同步
- 玩家下线时强制关闭仓库并保存
- 插件关闭时同步收尾保存

### 必拦截操作

对于管理员只读模式，必须拦截：

- 普通点击
- Shift 点击
- 数字键换位
- 拖拽
- 双击聚合
- Q 丢弃

### 物品限制建议

首版配置里建议预留：

- 黑名单物品
- 是否允许潜影盒

因为 `1.12.2` 已存在潜影盒，如果你的服务器物品体系比较复杂，这项最好可配置。

建议结构：

```yaml

  type: mysql
  host: 127.0.0.1
  port: 3306
  user: root
  password: "123456"

  table-prefix: sw_
  use-ssl: false

warehouse:
  default-pages: 3
  max-pages: 5
  page-size: 45
  allow-shulker-box: true

    - BEDROCK

  auto-save: true
  auto-save-interval: 300

  save-on-quit: true
```

## 16. 最终建议

你这版需求其实非常适合做成一个“先上服可用”的精简产品。

我建议后续开发顺序固定为：

1. 先把主页和单页仓库存取做通
2. 再接 MySQL
3. 再加多页切换
4. 最后补管理员只读查看

这样开发和排错成本最低。
